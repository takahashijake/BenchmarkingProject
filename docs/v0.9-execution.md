# BenchForge v0.9 candidate execution (initial vertical slice)

## Scope and limitations

The `benchmark` command now supports bounded, process-isolated **candidate-level** concurrency. Existing `run`, `search`, `automl`, and `robustness` workflows remain sequential and unchanged. This does **not** implement resume, atomic experiment-level commits, cancellation, or task timeouts yet. Do not assume those safety properties.

Use `benchforge benchmark configs/examples/breast_cancer_suite.yaml --workers 1` for legacy sequential semantics, or `--workers 2` to run up to two independent candidate processes. Candidate tasks receive the same precomputed CV folds. Aggregation, per-fold predictions, and leaderboard ranking use existing code; `ProcessPoolExecutor.map` collects in configuration order, independent of completion order. The existing default is 1 worker. A custom model registry requires single-worker execution.

### Resource model

A worker is an **OS process evaluating one complete candidate across its folds**. It is not a thread inside an estimator, nor a parallel Optuna trial. Each worker limits BLAS/OpenMP thread pools to one via `threadpoolctl`. Parallel mode rejects explicitly supplied `n_jobs` values other than 1 to avoid estimator joblib oversubscription. Sequential mode preserves previous estimator settings. Parallel runs have additional serialization and process startup overhead, and can use more RAM due to dataset copies. Choose based on the number of candidates, fitted model cost, and available physical resources, not logical CPU count alone. The CLI refuses worker counts above detected logical CPUs. It does not measure memory capacity or cgroup quotas.

### Reproducible measurements

Install with `python -m pip install -e '.[dev]'`, then run on the *same isolated machine* with a stable CPU allocation. For example:

```bash
for n in 1 2 4 8; do
  echo "WORKERS=$n"
  /usr/bin/time -v benchforge benchmark configs/examples/breast_cancer_suite.yaml --workers "$n" \
    >"/tmp/benchforge-$n.stdout" 2>"/tmp/benchforge-$n.time"
  grep -E 'User time|System time|Percent of CPU|Elapsed \(wall clock\)' "/tmp/benchforge-$n.time"
done
```

Use an example with **at least 8 candidates** to measure actual scaling at 8 workers: the supplied breast-cancer suite has five, so its 8-worker result is capped at five concurrent candidate fits. On Linux, `/usr/bin/time -v` reports aggregate CPU use of subprocesses, useful for relative CPU saturation. Divide the measured 1-worker wall duration by the N-worker wall duration to compute speedup. Record CPU model, physical/logical cores, RAM, sklearn and BLAS versions, repetitions, and variance. The command above is a measurement recipe, **not benchmark evidence**.

### Risks and next iteration

1. Implement a versioned, immutable task key including resolved dataset digest, CV fold definition, candidate specification, seed, preprocessing, metrics, and runtime compatibility.
2. Persist completed candidates in per-task temporary directories with fsync and atomic rename, then verify manifests before resuming. Do not mutate currently sealed result directories.
3. Add a persistent work manifest, interruption recovery, cancellation and enforceable process termination.
4. Add stage-level wall/CPU profiling and process resource telemetry to a separate diagnostic log (not result JSON).
5. Add nested-CV-specific safe task partitioning with explicit protection of outer validation folds.

CI should verify fold/prediction equivalence and failure isolation. Because benchmark tasks can be short, **speedup is not guaranteed**.
