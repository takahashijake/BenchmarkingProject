## Internal implementation plan

- A package publishes one `benchforge.providers` entry point per provider ID.
  Listing reads package metadata only. Inspection and explicit experiment
  activation load the selected factory, which returns a frozen provider bundle.
- API version 1 uses typed immutable declarations plus the existing Dataset,
  ModelSpec and SearchSpace interfaces, and a small metric callback contract.
  No second training, splitting, scoring orchestration or checkpoint system.
- Configurations pin provider implementation versions. Resolved declarations
  enter canonical configuration and fingerprints. Distribution versions are
  separate provenance, outside scientific identity. Empty provider fields are
  omitted to preserve built-in-only historical fingerprints.
- Registry composition copies mappings, sorts identifiers, and rejects duplicate
  names, unsafe IDs, unsupported APIs and mismatched callback declarations.
  Discovery failures never mutate the built-in registry instances.
- Activation occurs at workflow boundaries. Offline verification validates
  declarations as data and never activates a provider. Custom metric callbacks
  cannot be recomputed offline; verification must report that limitation.
- Initial execution support: serial run, benchmark, nested search, AutoML and
  robustness; serial benchmark checkpoint recovery. External providers with
  workers or hard budgets fail before imports or training. A later provider-ID
  worker bootstrap needs its own transport and startup regression coverage.
- Tests must cover installed-package discovery/activation, every extension
  category, canonical identity, invalid declarations, checkpoint incompatibility,
  offline verification, task compatibility, and unchanged scientific behavior.

## Alternatives and trust

Automatic registration on import would let unrelated installations change
experiments. Source-file or arbitrary object loading would weaken provenance and
worker reconstruction. Entry points offer offline package metadata and explicit
activation with ordinary Python installation tooling. Activated plugins are
trusted Python executable code, not a secure sandbox. Declared versions do not
prove source authenticity or bit-for-bit reproducibility.

## Implemented lifecycle and version strategy

1. Parse strict configuration and version pins without importing provider code.
2. Reject unsupported external execution policies before discovery or activation.
3. Discover installed entry-point metadata and load only selected factories.
4. Revalidate manifests and callback coverage; compose fresh immutable mappings.
5. Bind a configuration copy to its runtime; record canonical declarations.
6. Validate/copy dataset content and supplement its declared identity with a digest.
7. Delegate planning, folds, preprocessing, fit, metrics, ranking and failures to
   existing workflow kernels. Child run configs retain the resolved runtime.
8. Checkpoint serial benchmark candidates through the existing JSON adapter,
   compatibility identity, lock and atomic writer.
9. Seal configuration, provider declarations and separate installed provenance
   using existing artifact stores. Offline verification validates data only.

The provider API is explicitly version 1, independent of config schema 1,
artifact schemas, workspace schema 1 and the package's historical evaluator
version. Unknown APIs fail closed. Implementation and metric-semantics versions
are explicit semantic-version strings; space versions retain existing integer
semantics. Future incompatible changes need a new API version and migration
policy. Existing built-in enum members, config loaders, workflow APIs and
custom-registry serial execution remain available.

All selected declarations are scientific identity in v1. A finer used-component
identity was considered but deferred: AutoML policy can inspect an entire activated
registry, and silently omitting policy-relevant capabilities would weaken identity.
Unselected installed providers never influence the resolved experiment.

## Migration and limitations

No external provider selection is inferred from installed packages. Existing
configs require no migration and omit empty extension fields during canonical
serialization. Built-in-only scientific fingerprints and legacy checkpoint
compatibility retain their established inputs. Activated experiments persist
`provider_schema_version: 1`; missing, inconsistent or unsupported provider
metadata is rejected at artifact boundaries. Candidate checkpoint corruption is
recomputed under the existing recovery contract.

V1 supports serial provider workflows and serial fixed-benchmark resume. It
rejects external providers with parallel workers or hard budgets. Custom metric
callbacks are not run by verification or catalog ingestion: an explicit warning
limits the interpretation of deep verification. There are no probability-matrix
metrics, sandbox guarantees, parameterized dataset loaders, remote installation,
hot reload, dynamic global registration or plugin-specific training machinery.
