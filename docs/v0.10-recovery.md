# BenchForge v0.10: durable fixed-benchmark recovery

## What is supported

Candidate-level checkpointing is **opt-in for `benchmark` only**. `run`,
`search`, `robustness`, and `automl` retain their existing execution models.
The workspace is **not** a published experiment and must never be verified or
cataloged in place. Once the benchmark finishes, BenchForge writes the normal
versioned, sealed benchmark result and the existing verifier/catalog continue
to operate unchanged.

```bash
python -m pip install -e '.[dev]'
benchforge benchmark configs/examples/breast_cancer_suite.yaml --workers 2 \
  --workspace artifacts/recovery/example
# If interrupted, rerun with the same configuration (worker count may differ):
benchforge benchmark configs/examples/breast_cancer_suite.yaml --workers 2 \
  --resume artifacts/recovery/example
# Verify/catalog the "Artifacts:" *published* path shown at completion:
benchforge verify <published-artifact-directory>
```

The command prints the number and names of reused candidates, the number newly
evaluated and any invalid checkpoints that required recomputation. A fresh
`--workspace` must not already exist. `--resume` requires an existing,
compatible workspace. A successful run can also be resumed: it reuses verified
candidate work and publishes a new, independently sealed experiment. It does
not mutate historical seals. Python API: `run_benchmark_suite(config,
checkpoint_dir=Path("..."))` and `run_benchmark_suite(config,
checkpoint_dir=Path("..."), resume=True)`.

## Architecture decision and alternatives

Candidate-level recovery is the smallest safe boundary because V0.9 already
executes one independently valid, complete CV candidate at a time. Fold-level
checkpoints would require new partial `RunResult` semantics, and a transactional
scheduler/database would duplicate existing artifact and orchestration code.
Neither is justified for this vertical slice. A later extension could reuse
these identities but must not imply nested-search recovery already works.

A workspace contains a versioned `workspace.json`, a `tasks/` directory
with completed immutable logical candidate results, and an OS-managed lock
file alongside the workspace directory. There is no pickled estimator or
executable model state. Each candidate checkpoint carries a schema version,
experiment identity, candidate task key, explicit JSON payload and SHA-256
digest. The overall identity incorporates the resolved dataset values and
schema, exact fold index plan, canonical benchmark semantics, model
configuration, relevant dependency versions, and a deliberate execution
contract version. Output directory, worker count, runtime and timestamps do
not participate in identity. Source changes affecting evaluator semantics
must bump the execution contract.

A coordinator (not a worker) publishes each completed candidate through a
same-directory temporary file, file synchronization and `os.replace`, with
directory synchronization where supported. It does not write success for a
failed or interrupted fit. A corrupt/truncated/missing candidate checkpoint
is diagnosed and recomputed; an incompatible workspace manifest is rejected
before fitting. Unexpected files and symlinks under `tasks/` are rejected.
An exclusive OS-backed file lock serializes concurrent attempts to use one
workspace and is released on process exit, including termination. This is
cooperative filesystem safety rather than a signed security boundary against
an actively malicious user changing files concurrently.

The coordinator reconstructs the normal deterministic configuration-order
benchmark result, then calls the **existing** `BenchmarkArtifactStore` and
verification/sealing primitives. Candidate success/failure results, fold
predictions, metric semantics, and published schema are unchanged. Recovering
a task does not guarantee recovery of a *partially fitted candidate*: it must
be retrained from the beginning.

## Boundaries and failure behavior

- No resume with an unversioned custom model registry: a custom factory could
  change while retaining a misleading name.
- No resume of failed candidates; they are attempted again and their failures
  remain explicit. A crash during publication leaves at most an unused
  `.tmp` file; no unsealed bytes count as complete candidate work.
- Process crashes can discard in-flight fits, but already committed candidate
  checkpoints survive. This version does not promise hard cancellation or
  enforced wall-time/memory budgets.
- The lock prevents *cooperative* concurrent use on filesystems supporting
  OS file locks. Locking and atomic rename durability on exotic or networked
  filesystems depend on their actual filesystem semantics.
- The SHA-256 envelope detects accidental corruption, not adversarial
  re-signing. No arbitrary checkpoint pickle or model object is loaded.
- Version changes or dataset/split/config changes result in a clear
  incompatibility error, not a potentially invalid reuse. To change the
  experiment, create a new workspace.
- Candidate-level serial and parallel modes have the same scientific
  semantics, but durations and scheduling/serialization overhead may differ.
  No universal speedup is claimed.

## Quality gates

Run `python -m pytest -q`, `ruff check .`, `mypy src/benchforge`,
`python -m pip check` and `python -m build`. Regression coverage includes
normal sequential/parallel equivalence, no-refit reuse, interrupted candidates,
checkpoint corruption and incompatible identities, OS-backed concurrent-use
rejection, unexpected symlinks, and sealed published artifact verification.
Python 3.12 and 3.13 are covered by CI. Performance claims require separate
recorded experiments with controlled resource allocation.
